1. Objective
Organizations running workloads on multiple cloud providers currently rely on each provider's own monitoring tools (e.g. AWS CloudWatch, Cost Explorer, Azure Cost Management) separately. These tools report cost and usage, but do not explain why costs are changing, do not span providers, do not flag abnormal cost behavior beyond simple threshold alerts, do not turn a forward-looking cost forecast into a concrete commitment decision (e.g. whether a Reserved Instance or Savings Plan is worth buying), and generally leave every savings recommendation as a manual task regardless of how low-risk it is. This system is built to address those gaps directly, using AWS and Azure cost data as the working environment.
2. Scope
The system collects and normalizes cost and usage data from AWS and Azure, forecasts near-term spend with per-service explainability, detects anomalous cost behavior, lets a user simulate the financial impact of a rightsizing recommendation before committing to it, recommends Reserved Instance / Savings Plan purchases based on forecasted usage, and automatically acts on low-risk savings opportunities while escalating higher-risk actions through a notify-and-wait process. All of this is presented through a single lightweight web dashboard.
The system is explicitly scoped to two cloud providers (AWS and Azure). Google Cloud Platform (GCP) integration is treated as a possible future extension, not a core deliverable of this phase.
Multi-Cloud Aggregation — collect and normalize AWS and Azure cost/usage data into one schema.
Explainable Forecasting — predict near-term spend per service, with attribution for each prediction.
Anomaly Detection — flag cost/usage behavior that deviates from the forecasted baseline.
What-If Simulations — project the cost impact of a hypothetical rightsizing action before it is taken.
Rightsizing Recommendations — identify and rank idle/underutilized resources by savings potential.
Savings Plan Optimiser — recommend Reserved Instance / Savings Plan purchases using break-even analysis.
Automated Remediation with Escalation — alert on budget threshold breaches and act automatically on low-risk savings, escalating to a more disruptive action only after notify-and-wait.
Dashboard — present all of the above through a single, lightweight web interface.
3. Functional Requirements

Priority is expressed as Must (core deliverable), Should (expected but not blocking), or Could (stretch/future extension). Implementation status against each requirement is tracked separately in Section 6.

4. Technology & Implementation Flexibility
Where a functional requirement names a specific technique or library as an example — such as Prophet, SARIMA, SHAP, or Isolation Forest — that name is illustrative of one way to satisfy the requirement, not a mandated technology. The binding obligation is the functional behavior described by the requirement (e.g. FR-2.4's obligation to attribute a forecast to a specific driver), not the specific library used to produce it.
This applies in particular to the following requirements, where alternative approaches are explicitly acceptable:
FR-2.2 / FR-2.4 (forecasting and attribution): any two comparable forecasting methods may be used in place of Prophet/SARIMA, and attribution may be produced via a model's native decomposition (e.g. trend/seasonality components), a secondary explanatory model, or another defensible method in place of SHAP.
FR-3.3 (unsupervised anomaly detection): any unsupervised method suited to multivariate usage/cost features may be used in place of Isolation Forest.
FR-6.1 (commitment pricing comparison): pricing data may be sourced from a static, periodically-updated reference table rather than a live pricing API, provided this limitation is documented.
This section does not remove any Must-priority obligation; it clarifies that the obligation is functional, not technological, giving implementation flexibility to select the most workable approach within the project timeline.

6.2 Explainable Forecasting (FR-2)
ID
Status
Implementation Note
FR-2.1
Completed
Per-service 30-day forecast implemented. Each service (EC2, RDS, S3, Lambda) is forecast independently then normalized so per-service values sum exactly to the headline total on every forecast day. is_normalized=True is asserted on every response row and verified by automated check (diff=0.0).
FR-2.2
Completed
Two forecasting models implemented: (1) Polynomial Regression (degree-2, scikit-learn) and (2) Holt's Double Exponential Smoothing (additive trend, pure-NumPy grid-search over alpha/beta). Both train on the same historical window, produce independent 30-day forecasts, and are evaluated head-to-head on the held-out window. The lower-MAPE model is selected as the headline forecast. Per Section 4, pure-NumPy Holt-DES is an acceptable substitute for Prophet/SARIMA.
FR-2.3
Completed
MAPE and RMSE reported on a held-out validation window. Rule: held_out = max(3, round(0.20 * n_days)); comparison skipped if n_days < 10 (would leave < 7 training points). Current live values: poly_mape=10.1%, poly_rmse=1.23, hw_mape=16.57%, hw_rmse=1.79 (46 training days, 9-day held-out window). R² score is also retained in model_info for reference.
FR-2.4
Completed
Service-contribution attribution implemented via per-service model decomposition. Each service's normalized 30-day forecast sum is expressed as a percentage of the headline total (attribution_pct). Current live attribution: EC2=54.1%, RDS=37.7%, S3=7.3%, Lambda=0.9%. Displayed as a bar chart in the Predictions UI. Per Section 4, native model decomposition is an acceptable substitute for SHAP.
FR-2.5
Completed
Predictions page renders five sections: (1) metric cards (predicted total, best model, MAPE, training days), (2) model comparison card with MAPE/RMSE per model and winner badge, (3) combined historical+forecast chart with Both-Models toggle, (4) per-service stacked area chart and attribution bars (NORMALIZED ✓ badge shown), (5) forecast data table with per-service columns and daily totals. All data from /predictions/ and /predictions/per-service endpoints.
6.3 Anomaly Detection (FR-3)
ID
Status
Implementation Note
FR-3.1
Completed
Cost/usage anomalies are flagged when actual daily cost deviates from the FR-2 polynomial/Holt-DES forecast baseline by |z| >= 2.5sigma. Detection runs independently for each service (EC2, RDS, S3, Lambda) AND for the TOTAL account-level daily cost aggregate (service_type='TOTAL'). Rows with |z| < 2.5 are never stored. TOTAL-level anomalies that survive the threshold are flagged with driver_service = the highest-ranked service from get_service_attribution().
FR-3.2
Completed
FR-2 forecast baseline is the direct input to the anomaly detector. The uncertainty band is derived empirically from the rolling distribution of historical forecast residuals (Option A — residual-derived band), using a 14-day rolling window. No fixed % tolerance is used.
FR-3.3
Completed
Unsupervised Z-score detector (primary) combined with IQR check (secondary). Z-score: z = (residual - rolling_mean) / rolling_std, lookback=14 days. IQR: flags if residual > Q3 + 1.5*IQR or < Q1 - 1.5*IQR. Per Section 4, Z-score + IQR is an acceptable unsupervised substitute for Isolation Forest given the current data volume (46 days x 4 services). Severity: |z| 2.5-3.5 = warning, |z| >= 3.5 = critical. NOTE: Current anomaly counts are measured against synthetic seed data (180 rows, source='synthetic_seed'), not live AWS billing. Real-world false-positive rates may differ once the account accumulates sufficient live AWS billing history.
FR-3.4
Completed
Driver service attribution uses get_service_attribution() — the shared helper in ml_predictor.py that FR-2.4 also uses for ranking. IMPORTANT: get_service_attribution() returns raw_attribution_pct — an un-normalized ranking signal (computed as service_raw_30d_sum / headline_30d_sum * 100). This value can exceed 100% for a single service and does NOT sum to 100 across services; it is used only for driver identification (which service most likely caused the anomaly), not for user-facing display. For user-facing normalized percentages (which sum to 100% and match the Predictions page), the /predictions/per-service endpoint is the authoritative source.
FR-3.5
Completed
Anomaly feed implemented: (1) Dashboard anomaly widget (critical/warning counts, top driver, link to /anomalies), (2) Dedicated /anomalies page with metric cards, residual timeline chart (spike=red, drop=blue), and sortable anomaly feed table (date, service, actual, forecast, deviation%, z-score, severity badge, direction, driver, resolve button). Anomalies API: GET /anomalies/ (list), GET /anomalies/summary (dashboard widget), POST /anomalies/{id}/resolve (user dismissal with is_resolved=True), POST /anomalies/refresh (manual re-detection trigger). Resolution is permanent — re-detection cycles skip is_resolved=True rows.

8. Assumptions & Constraints
Development window: the remaining implementation is expected to fit within the Design & Development phase of the project's Plan of Work.
Azure test data: FR-1.2 assumes availability of an Azure subscription (or sandbox/mocked billing data equivalent to the existing AWS demo mode) for development and testing.
Live remediation testing: per NFR-5, FR-7.2 and FR-7.4 will be validated against demo/sandbox data before being enabled against any live cloud account, to avoid disrupting real workloads during development.
Pricing data currency: FR-6.1's Reserved Instance / Savings Plan pricing may be sourced from a static, periodically-updated table rather than a live pricing API (see Section 4); this limitation will be stated explicitly in the final report.
